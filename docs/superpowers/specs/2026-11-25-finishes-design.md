# Step 15 · Finishes Design

Status: decided and built without the author (asleep), per « je veux que tu livres sans m'attendre ». The author reviews afterwards. Plan: [2026-11-25-finishes.md](../plans/2026-11-25-finishes.md). Built in a throwaway clone, stacked on `feat/library-timeline`.

Sources: the step 15 section of [2026-11-25-steps-13-16-brief.md](2026-11-25-steps-13-16-brief.md), its addendum [2026-11-25-photo-info-brief.md](2026-11-25-photo-info-brief.md) (committed with this spec), and the controller's brief for this run.

## Request

- PWA manifest (installable, `display: standalone`, icons), Apple meta tags. No service worker.
- Skeleton loaders instead of « Chargement… ».
- Offline banner and a « Réessayer » button on failed loads.
- Keyboards: `enterKeyHint`, `autoCapitalize="none"` on e-mails, `inputMode` where useful. The controller also asked for keyboard shortcuts in the viewer.
- Drag down to close the bottom sheet and the viewer, hand-made on Radix. No `vaul`.
- Pinch zoom and double-tap zoom in the viewer.
- Native share (Web Share API). The brief says « of the invitation link, falling back to copy »; the controller asks for sharing the photo outward from the viewer, distinct from « Envoyer à un ami ». Both are done (F21, F22).
- Viewer: an intermediate Cloudinary size (`srcset`) instead of the 1920 px one everywhere.
- Photo info panel (addendum): « Infos » (ⓘ) in the viewer; desktop side panel that shrinks the photo and stays open across next/previous; phones: bottom drawer on the existing sheet, half height, swipe down or ✕ closes; added date, sender and message, collections as links, dimensions and weight stored at upload (older photos show nothing); never a location.

Constraints of the run: no new dependency (explicitly no `vaul`, no `vite-plugin-pwa`, no service worker). A parallel step 17 (« Envoyer » page, tab bar Bibliothèque · Envoyer · Cadre · Amis) is stacked **before** this one: the tab bar, the add panel, the share flow and `LibraryHeader` are left alone so the rebase stays easy.

## Decisions

### PWA shell (`feat/pwa-shell`)

| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F1  | **A static `client/public/manifest.webmanifest`**: name and short name « FamilyFrame », `lang: fr`, `start_url` and `scope` `/`, `display: standalone`, white `background_color` and `theme_color` (the HTML `theme-color` metas, light and dark, still win while the page runs). Icons: 192 and 512 px PNG (`purpose: any`) and a 512 px maskable PNG. `index.html` links it and adds `apple-touch-icon` (180 px), `apple-mobile-web-app-title` and a `description`.                                                                                                                                                                                             | A static file is one more line to explain, `vite-plugin-pwa` is excluded. Chrome no longer requires a service worker to offer installation; iOS reads the touch icon and title from the HTML. |
| F2  | **A FamilyFrame icon replaces Vite's default logo** in `favicon.svg`: a cream frame holding a sky, a sun and two hills, on the frame's dark warm background. The PNGs were rendered once from two SVG sources with `sharp`, already a server dependency, by a throwaway script recorded in the plan; only the outputs are committed. The maskable one keeps its drawing inside the 80 % safe circle.                                                                                                                                                                                                                                                              | `favicon.svg` was still the Vite template's lightning logo. No design tool, no new dependency.                                                                                                |
| F3  | **No `apple-mobile-web-app-status-bar-style`**: the default status bar keeps dark text on the light theme.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | `black-translucent` would put white text over the white account bar in the light theme.                                                                                                       |
| F4  | **Skeletons** (`ui/skeleton.tsx`, the shadcn primitive: `animate-pulse rounded-md bg-accent`, plus `motion-reduce:animate-none`): the library's first load shows grid tiles or list rows shaped like the chosen layout under a day label; the viewer shows a dark block where the photo goes; the friends page and the invitations list show rows. Each skeleton group has `role="status"` and an `sr-only` « Chargement… », so screen readers still hear it. The frame keeps its status screen (« Chargement des photos… »): a wall screen is not a page being laid out. « Chargement… » on the « Charger plus » button stays: it is a button label, not a page. | The layout appears at once, so nothing jumps when the photos arrive. The shadcn primitive is ten lines, not a dependency.                                                                     |
| F5  | **Offline banner** (`useIsOnline`, `OfflineBanner`): `navigator.onLine` plus the `online` and `offline` events, through `useSyncExternalStore` like `useMediaQuery`. While offline, a strip under the account bar's content (inside the sticky header, so it stays in view) says « Pas de connexion. Les photos se mettront à jour au retour du réseau. » with `role="status"`. Not on the frame: it already handles a lost network on its own screen (R-CAD-51, R-CAD-55), and a wall screen should not show a banner.                                                                                                                                           | `navigator.onLine === false` is reliable (true can lie, but then the loads fail and F6 applies). The header is the one place every page with the account bar shares.                          |
| F6  | **« Réessayer » on a failed first load.** The library's first page: `usePhotoLibrary` gains `hasLoadFailed` and `retry`; a failed first load shows « Les photos n'ont pas pu être chargées. » and « Réessayer ». `retry` bumps a counter in the connection effect's dependencies: the socket reconnects and its `connect` reloads, the same path as a reconnection. The friends page and the invitations list already had `error` and `reload`: their error alert gains a « Réessayer » button. « Charger plus » that fails already stays as a button to press again.                                                                                             | Before, a failed first load left « Chargement… » forever. Reusing the reconnect path adds no second loading code.                                                                             |
| F7  | **Mobile keyboards**: every e-mail field gets `autoCapitalize="none"`, `autoCorrect="off"`, `spellCheck={false}` (in `TextField` for `type="email"`, and the login field); `enterKeyHint` on the last field of each form: « go » for login and account creation, « send » for an invitation and a friend request, « done » for a name or a password change. No `inputMode`: `type="email"` already brings the e-mail keyboard, and no field takes numbers.                                                                                                                                                                                                        | A capital first letter broke e-mail logins on phones; the return key says what it does.                                                                                                       |

### Viewer gestures (`feat/viewer-gestures`)

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Why                                                                                                                                                |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| F8  | **`BottomDrawer`** (`components/panel/BottomDrawer.tsx`): the existing `Sheet` from the bottom, with a grab handle at the top (a 48 × 6 px bar in a full-width, 24 px tall zone, `touch-none`). `useDragToClose` follows the pointer on the handle only, moves the sheet with the CSS `translate` property (it composes with the enter animation's `transform`), closes past 100 px and springs back otherwise; the spring is skipped under `prefers-reduced-motion`. `ResponsivePanel`'s phone sheet uses it. ✕ and Escape still close it. | Dragging only from the handle leaves the sheet's own lists free to scroll. About 60 lines, as the brief planned, instead of `vaul` (unmaintained). |
| F9  | **Drag down to close the viewer** (touch only): a vertical finger move on an unzoomed photo moves it down and fades it; released past 100 px, the viewer closes like ✕, else it springs back. Embla already lets go of a touch whose first move is vertical (its cross-axis check), so the carousel and the drag do not fight. The mouse keeps ✕ and Escape.                                                                                                                                                                                | The phone gesture people expect from photo apps. Alternatives stay: ✕, Escape, the back button.                                                    |
| F10 | **Pinch zoom, double-tap, double-click and keys.** One hook, `useViewerGestures`, reads pointer events on the photo: two fingers pinch around their midpoint (1× to 4×); one finger (or the mouse) pans a zoomed photo, kept within the photo's box; a double tap or a double-click zooms to 2.5× on that point, or back to 1×. The keys `+` (or `=`) and `-` zoom in and out by steps, centred. The zoom maths are pure functions in `viewer/zoom.ts`.                                                                                     | `touch-action: none` on the photo stops the browser from zooming the whole page, so the hook gets every finger.                                    |
| F11 | **A zoomed photo does not swipe**: Embla's `watchDrag` is a function reading a ref, false while zoomed, so the finger pans instead. Changing photo (arrows, keys) or closing resets the zoom. While zoomed, the image's `sizes` grows so the browser fetches the larger file (F20).                                                                                                                                                                                                                                                         | Panning and swiping cannot share one finger.                                                                                                       |
| F12 | **A tap that ended a gesture does not toggle the controls**: the click that follows a pan, a drag or a pinch is ignored. A double tap still toggles the controls twice (they flicker back to where they were), which is accepted.                                                                                                                                                                                                                                                                                                           | Waiting 300 ms to tell a tap from a double tap would slow every tap.                                                                               |
| F13 | **Viewer keys**: ← → change photo (step 13), Escape closes, `+`/`-` zoom, `i` opens or closes « Infos » (F17). They are ignored with Ctrl, Alt or Meta held, and while a menu or a dialog is open over the viewer (`isOverlayOpen`).                                                                                                                                                                                                                                                                                                        | Browser shortcuts (Ctrl + +) keep working; a menu keeps its own keys.                                                                              |

### Photo info (`feat/photo-info`)

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Why                                                                                                                                                                           |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F14 | **Width, height and bytes stored at upload.** Cloudinary's upload answer already gives the stored image's `width`, `height` and `bytes`: `UploadedImage` carries them, `storeNewPhoto` saves them (`Photo.width`, `height`, `bytes`, optional `Int` in Prisma), and a photo shared from the library copies them from the original, since it points to the same image. The API's `Photo` gains `width`, `height` and `bytes`, each `null` on photos stored before.                                                                          | « What the server already measures »: no extra sharp call, no EXIF parser, no new dependency. The numbers describe the kept image (up to 4096 px), the one a print would use. |
| F15 | **The rule is unit tested** (`photos.service.test.ts`, `photos.service.share.test.ts`): an upload stores the three numbers; a library share copies them. Bruno: `create/01` asserts numbers, `list/01` asserts that every photo has the three fields, a number or `null`; `share/02` asserts the copy keeps the original's numbers.                                                                                                                                                                                                        | AGENTS.md: a service rule and an endpoint change carry their tests.                                                                                                           |
| F16 | **Content of the panel** (`PhotoInfo`): « Ajoutée » with the date and time (« Aujourd'hui à 14:05 », « Hier à 09:12 », else « dimanche 22 novembre 2026 à 14:05 »); for a received photo « Envoyée par » with the name and the message; « Collections » with one link per collection holding the photo, read from the collections already loaded (`CollectionsContext`), or « Dans aucune collection »; « Image » with « 4032 × 3024 · 2,4 Mo » when the numbers exist, nothing otherwise. Never a location, nothing about the recipients. | Only what we know. The collections are already in memory: no request.                                                                                                         |
| F17 | **Entry**: a ⓘ button « Infos » in the viewer's top bar, before « Mode cadre », with `aria-expanded` and `aria-controls`, and the `i` key.                                                                                                                                                                                                                                                                                                                                                                                                 | The brief puts it beside the ⋯.                                                                                                                                               |
| F18 | **Desktop (≥ md)**: an `aside` of 360 px on the right of the viewer; the photo area (carousel, caption, top bar) becomes the left flex column and shrinks, Embla re-measures on resize. Its open state lives in `sessionStorage` (read and written in `try`), so next/previous and the next photo opened keep it, until the tab closes. The panel has its own ✕.                                                                                                                                                                           | As Google Photos does: the photo is never covered. Per tab, not per account.                                                                                                  |
| F19 | **Phones**: the same content in a `BottomDrawer` (F8) inside the viewer, `h-[50svh]`, the photo dimmed above it. It always starts closed and closes with ✕, Escape, a tap above it or a drag down. A collection link opens the library filtered on it, replacing the viewer's history entry, so Back returns to the library, not to the photo.                                                                                                                                                                                             | Half a screen keeps the photo in sight. A drawer that reopened on every photo would cover the swipe.                                                                          |

### Share and sizes (`feat/share-srcset`)

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Why                                                                                                                                                                                                                                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F20 | **A 1280 px intermediate size**: `deliveryUrls` adds `mediumUrl` (`c_limit` 1280 px, signed like the others, so strict transformations accept it with no list to maintain). The viewer's `img` gets `srcSet="<mediumUrl> 1280w, <url> 1920w"` and `sizes="100vw"`, or `400vw` while zoomed so the browser switches to the larger file. The frame keeps `url` (a TV wants 1920). Bruno and `cloudinary.test.ts` check the new transformation and its signature.                                                                                                                                                                 | One more size only: 640 is the cropped square thumbnail and cannot serve a whole photo. A phone (360–430 CSS px at 2–3×) takes 1280 instead of 1920, about half the bytes. The `w` descriptors are the box size: for a portrait photo the real width is smaller, and the browser may pick a little higher than needed, which is acceptable. |
| F21 | **« Partager… » in the viewer's ⋯ menu**, through the menu's existing `children` slot (no change to `PhotoActionsMenu`), only where `navigator.canShare({ files })` accepts an image file. It fetches the 1920 px file (Cloudinary answers with CORS headers), builds a `File` named after the photo's day, and calls `navigator.share({ files })`. Closing the share sheet is silent; any other failure says « La photo n'a pas pu être partagée. ». The label and the icon (`Share2Icon`) differ from « Envoyer à un ami » (`SendIcon`): the first leaves FamilyFrame through the phone's own apps, the second stays inside. | Sharing a file, not a link: a signed Cloudinary link would hand out a permanent public address to the photo.                                                                                                                                                                                                                                |
| F22 | **The invitation link can be shared** with the system share sheet (« Partager le lien ») where `navigator.share` exists, next to « Copier le lien », which stays.                                                                                                                                                                                                                                                                                                                                                                                                                                                              | The brief's own item: an admin on a phone sends the link through a messaging app.                                                                                                                                                                                                                                                           |

## Open questions

1. **EXIF (date taken, camera)**: needs an EXIF parser dependency, and step 14's client downscale drops EXIF for large files. Not done; ask the author.
2. **An editable description** of one's own photos (Google's « Ajouter une description »): a new feature, not done.
3. **Bruno and Chrome were not run here**: the clone has no server env file, so the API and Vite cannot start. The controller runs them (plan, Final verification).
4. **iOS share sheet timing**: Safari wants `navigator.share` inside the tap's activation; the file is fetched first (usually from the HTTP cache). If a slow network loses the activation, the error toast shows and a second tap works. To check on an iPhone.
5. **No offline cache**: without a service worker an installed FamilyFrame shows the browser's offline page when opened with no network. Accepted by the brief.
