# Step 10: collections

- Date: 2026-11-25
- Scope: step 10 « Collections ». A member names lists of their own photos (« Noël », « Les vacances »), files photos into them from the photo « … » menu, and lets the frame play the whole library or one collection, in order or shuffled. Server (schema, six endpoints, one socket event, Bruno) and client. **No new dependency, Prisma stays on v6.**
- AI usage: the author asked the AI to design and deliver steps 8 to 11 without waiting for a design session (« je veux que tu livres 8 à 11 sans m'attendre, c'est tout l'intérêt des PR stackées. Rien n'est mergé », 2026-11-25). Every decision below was taken by the AI from the goal's brief, with its reason; the author reviews them afterwards on the draft PRs. The ones most worth a second look are listed under Open questions. Early in the run, before the controller forbade Docker for this work, the AI verified the Prisma/MongoDB query semantics on a throwaway MongoDB container (port 27099, database `s10verify`); the container is gone and Docker was not used afterwards. The `photoIds: { equals }` filter of the conditional remove, added after that, was **not** run on a database: it rests on Prisma's documented scalar list filters (`equals`, supported on MongoDB) and on extended unique `where` in `update` (GA since Prisma 5), and is typed by the generated client. The AI built every task in a throwaway clone (gates green) before writing the plan, and had a fresh-context reviewer read the whole diff (its findings are folded in, see the plan's Drift Log).
- Builds on: `2026-11-25-photo-mail-design.md` (`isOpened`, the opened filter, `photo:deleted`), `2026-11-25-frame-mode-design.md` (`useFrameMode`, `usePlaybackPhotos`, `RadioSubmenu`, `frameSettings.ts`, `FrameSettingsCard`), `2026-11-24-photo-experience-design.md` (the « … » menu, the viewer).

## Goal

The library grows; the frame should not always play all of it. A member makes a « Noël » collection, ticks it in the « … » menu of a few photos, and puts « Noël » on the living-room frame for December, shuffled. The collection is private, like the library, and keeps up on every device without a reload.

## Brief (from the goal)

- Create, rename and delete a collection.
- Add a library photo to a collection, or remove it, from the « … » menu and from the viewer.
- The frame plays the whole library or one collection, in a linear loop or in random order.
- Keep the photo source open for step 11 (« Sélection du jour », « Radio » over the same collections).
- An unopened received photo never appears in a collection and cannot be added to one.

## Decisions

| Topic                           | Decision                                                                                                                                                                                                                                                                                                               | Main reason                                                                                                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Membership storage              | `Collection.photoIds String[] @db.ObjectId`, on the collection; the photo does not know its collections                                                                                                                                                                                                                | one document per collection, read in one query; the `Photo` DTO and its events stay unchanged                                                                     |
| `photoIds` at creation          | written `[]` explicitly                                                                                                                                                                                                                                                                                                | verified: a create without it stores no field, and `NOT: { photoIds: { has } }` then never matches (MongoDB finds « does not contain » only on an existing field) |
| Add                             | one `update` filtered on `{ id, ownerId, NOT: { photoIds: { has: photoId } } }` with `push`; P2025 → re-read: absent collection = 404, present = already in, answer it as is (idempotent, `200`)                                                                                                                       | verified: two concurrent adds of the same photo store it once; no read-modify-write race on add                                                                   |
| Remove                          | read, filter, then `set` only if the list is still the one read (`where: { id, ownerId, photoIds: { equals: readIds } }`); on no match, re-read and retry once; a second miss → 500; already absent → answer as is (idempotent)                                                                                        | Prisma 6 has no `$pull`; the conditional write keeps an add made from another device in between instead of overwriting it                                         |
| Dead ids                        | a deleted photo's id stays in `photoIds`; every read keeps only ids still in the owner's opened library (`findLivePhotoIds`, one `findMany` for all collections)                                                                                                                                                       | no cascade to write in the photo delete path; the lists are small                                                                                                 |
| Which photos can be added       | `hasOpenedPhoto(ownerId, photoId)`: the owner's photo, opened or legacy (`IS_OPENED`, exported from the photos repository)                                                                                                                                                                                             | the brief: an unopened received photo never enters a collection                                                                                                   |
| Photo id                        | lowercased after the format check, as MongoDB answers ObjectIds: a capitalised id matches the stored one; `OBJECT_ID_PATTERN` is shared with the photos feature                                                                                                                                                        |
| Refused photo                   | unknown, foreign or unopened → `404 PHOTO_NOT_FOUND`                                                                                                                                                                                                                                                                   | the same existence-hiding rule as delete and open; no new code                                                                                                    |
| Names                           | trimmed, 1 to 50 characters, not a string → `400 COLLECTION_NAME_INVALID`; unique per owner, exact match (`@@unique([ownerId, name])`, P2002 → `409 COLLECTION_EXISTS`); renaming to the same name is allowed                                                                                                          | 50 fits a menu line and a toggle; the index makes uniqueness atomic; exact match keeps the rule explainable                                                       |
| Order                           | sorted by name, `localeCompare(…, 'fr')` (« Été » before « Noël »), server and client                                                                                                                                                                                                                                  | MongoDB's default sort is byte order; the list is small enough to sort in memory                                                                                  |
| Unknown collection              | foreign, unknown or malformed id → `404 COLLECTION_NOT_FOUND`                                                                                                                                                                                                                                                          | a malformed id is just one more unknown id; nothing leaks                                                                                                         |
| API                             | `GET /api/collections` → `200 { collections }`; `POST` `{ name }` → `201`; `PATCH /:id` `{ name }` → `200`; `DELETE /:id` → `204`; `PUT /:id/photos/:photoId` → `200 Collection`; `DELETE /:id/photos/:photoId` → `200 Collection`                                                                                     | REST-ish; `PUT` because adding is idempotent; membership calls answer the collection so the client applies it at once                                             |
| DTO                             | `Collection = { id, name, photoIds }`, never the owner                                                                                                                                                                                                                                                                 | the same shape the client needs for counts and checkboxes                                                                                                         |
| Socket event                    | every write emits `collections:changed`, no payload, to the owner's room; each page re-reads `GET /api/collections`                                                                                                                                                                                                    | one listener; the server stays the only source; one event per kind of change would need as many listeners                                                         |
| Logs                            | `collection.created`, `.renamed`, `.deleted`, `.photo_added` (only on an actual add), `.photo_removed`: ids only, never the name                                                                                                                                                                                       | the name is personal content (security logging rule)                                                                                                              |
| Seed                            | `collection.deleteMany()` before the users                                                                                                                                                                                                                                                                             | Prisma emulates relations on MongoDB: deleting a user with a collection fails with P2014 (verified)                                                               |
| Client state                    | `CollectionsProvider`, mounted once behind `RequireAuth` (`LoggedInLayout`), shared by the library card, the photo menus, the frame and the preferences (`useCollections`)                                                                                                                                             | one list per tab, read everywhere; the frame needs it too                                                                                                         |
| Client live updates             | the provider has its own Socket.IO connection and re-reads on connect, on `collections:changed` and on `photo:deleted`; the latest load wins; a failed reload keeps the list shown                                                                                                                                     | the same live-load pattern as the feed, the library and the mail                                                                                                  |
| Client writes                   | a successful action applies the collection answered (`withCollection`) without waiting for the event                                                                                                                                                                                                                   | the menu checkbox follows the click at once                                                                                                                       |
| Library UI                      | a « Mes collections » card between the upload card and the library section: « Nouvelle collection », one row per collection with its photo count and a « … » menu (« Lire sur le cadre », « Renommer », « Supprimer »); after a deletion, focus goes to « Nouvelle collection » (the row and its menu button are gone) | collections belong to the library page; no new route to learn                                                                                                     |

The union leaves room for step 11                              |
| Source as a string              | `sourceKey` / `sourceFromKey` (`library`, `collection:<id>`)                                                                                                                                                                                                                                                           | radio items and toggle items only carry strings                                                                                                                   |
| Frame photos                    | `useSourcePhotos` filters the frame's feed with the collection's `photoIds`; order stays newest first                                                                                                                                                                                                                  | no extra request; an unopened photo, absent from the feed, never plays; membership changes follow `collections:changed`                                           |
| Unknown collection on the frame | deleted, or the list failed to load → the library plays; while the list loads → « Chargement des photos… »                                                                                                                                                                                                             | a frame on a wall must show photos rather than an error; a deleted collection must not leave it blank                                                             |
| Empty collection on the frame   | new status `emptyCollection`: « Cette collection est vide. » — « Ajoutez-y des photos depuis la bibliothèque. »                                                                                                                                                                                                        | silently playing the library would hide the choice made                                                                                                           |
| Source change                   | starts on the newest photo of the new source (`useRestartOnSourceChange`, during render) and draws a new shuffle round starting on that photo (the hook returns the newest id in the render of the change; `usePlaybackPhotos` keyed by source); the first source known after loading is no change                     | the previous pick and the arrivals count belong to the old source; `/frame?photo=<id>` keeps its photo                                                            |

## Rejected

- **`Photo.collectionIds`** (membership on the photo): every photo DTO and event would grow, and deleting a collection would update many photos.
- **A join model (`CollectionPhoto`)**: one more model and one more query per read, for lists a single person edits.
- **A cascade on photo delete** to clean `photoIds`: Prisma 6 has no `$pull`; filtering on read is one query and never wrong.
- **`POST /:id/photos` with a body** for add: `PUT` on the member path is idempotent by nature and needs no body to validate.
- **Case-insensitive name uniqueness**: needs a normalized second field and index; exact match is simpler to explain (Open question 3).
- **A payload on `collections:changed`** (the changed collection): each client would need merge logic for create, rename, delete and membership; a re-read is one small request.
- **Sharing the feed's socket** with the provider: a refactor of `photoSocket.ts` and three hooks (Open question 4).
- **A `/collections` page**: the card in the library is enough for create, rename, delete; viewing a collection's photos is the frame's job for now.
- **Silently falling back to the library for an empty collection**: the person would not know why their choice is ignored.

## Out of scope

Sharing a collection with a friend; a cover photo; ordering collections or the photos inside one; filing several photos at once; a page listing a collection's photos; nested collections; playing several collections together; the day's selection and the radio (step 11).

## Open questions (defaults applied meanwhile)

1. **Membership on the collection, ids filtered on read, never pruned** (default): a deleted photo's id stays in `photoIds` and is dropped on every read. Alternative: a join model, if step 11's radio needs « collections of this photo » often (today it would scan the owner's collections, a handful).
2. **Remove retries once** (default): the conditional write misses when the list changed; after one re-read and a second miss the server answers 500 rather than lose a write. Alternative: a retry loop with a bound.
3. **Names unique by exact match** (« noël » and « Noël » can coexist) (default). Alternative: compare lowercased, unaccented names.
4. **A third Socket.IO connection** on the library and the frame (feed or library, mail, collections), documented in ARCHITECTURE (default). Alternative: one shared socket per tab.
5. **An empty collection keeps the frame on its own screen** (default) instead of playing the library; the screen only offers « Retour à la bibliothèque », no way to switch to the library from the frame itself. Alternative: a « Lire toute la bibliothèque » button there.
6. **`/frame?photo=<id>` with a photo outside the played collection starts on the collection's newest** (R-CAD-83) (default). Alternative: switch the frame to the library for that visit.
7. **The source is per device**, like the other frame settings (default). Alternative: per account, so every frame of the family plays the same collection.
8. **The create dialog says « rangez-y vos photos depuis leur menu « … » »** even when opened from that menu (where it files the photo itself). Alternative: a second description for that case.
9. **A failed collections load plays the library**, then switches to the collection when a later load succeeds (R-CAD-81). Alternative: show the failed screen.
10. **While the collections load, the preferences' « Photos » shows « Toute la bibliothèque » as chosen** (the played source falls back to the library until the list arrives). Alternative: disable the group while loading.
